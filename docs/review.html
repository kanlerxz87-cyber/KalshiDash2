Findings

Method

  1. Read every file in the repository and listed each factual claim it makes about Kalshi — endpoints, field names, enum values, authentication rules and semantics.
  2. For each claim, opened the corresponding page at docs.kalshi.com and compared it field by field.
  3. Cross-checked ambiguous shapes against the official kalshi-typescript SDK, which is generated from Kalshi's OpenAPI specification, and against live demo API responses recorded in data/meta.json.
  4. Wrote a checker that parses the site and fails the build when a page links to a missing file or uses a field name that is not in the official schema (scripts/verify_site.py).

Known limit: the review is of repository content at the commit shown in the footer of the merged pull request. Kalshi can change its API at any time; the collector will show a broken field as an error rather than as a quietly wrong number.
