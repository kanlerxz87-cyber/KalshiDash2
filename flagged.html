Flagged for review

Irregularities found while verifying this repository and the Kalshi demo API, plus everything that could not be confirmed. Nothing on this page blocks the site from working; each item is here so it can be reviewed and accepted, fixed, or rejected deliberately.

How to read this page

Every item has an ID, the evidence that produced it, and an official source link. Items marked open are unresolved; mitigated means the site handles the problem explicitly rather than hiding it.

Two items (F6, F7) describe defects in the previously published version of this site, found by re-checking it line by line. They are recorded here rather than deleted, because the record of a fix is itself evidence.

1 · Defects found in the previously published site

Found by reading the merged docs/ implementation against the official documentation, then reproducing each rule in a deterministic test.

F6 — Authenticated requests could never have succeeded open

What was found: the earlier docs/assets/app.js made two mistakes in request signing:

  1. It imported the private key with crypto.subtle.importKey("spki", …). A private key PEM is PKCS#8, not SPKI — the import rejects it.
  2. It signed timestamp + METHOD + "/portfolio/balance". Kalshi requires the path to include the API prefix: /trade-api/v2/portfolio/balance. The query string must be stripped, but the prefix must stay.

Evidence: the deterministic self-test tools/verify/auth-sign-test.mjs asserts both rules. It passes 6/6: the SPKI import of a private key fails, and a signature over the shortened path does not verify.

Impact: balance, positions, fills and every order would have returned HTTP 401 on the published site, so portfolio tracking and trade execution could not work.

Status here: fixed in site/assets/js/kalshi.js — the key is imported as PKCS#8 (or PKCS#1, wrapped appropriately), and the signed path is /trade-api/v2 + path with the query stripped.

Sources: API keys ↗ Authenticated requests ↗

F7 — The order form mislabelled side semantics open

What was found: the earlier order form offered <option value="ask">Sell Yes (ask)</option>. In the API's book vocabulary ask ≡ no: sending side: "ask" buys a NO position, it does not sell a YES position.

Evidence: the documented direction table states buy no → outcome_side no → book_side ask.

Impact: a user who selected "Sell Yes" would have opened the opposite position.

Status here: the new form asks directly whether the user is buying YES or NO and maps it to bid/ask internally.

Source: Order direction ↗

F8 — Topic matching was applied to a truncated series list, and gas had no category mitigated

What was found: the earlier dashboard discovered topics by substring-matching keywords against GET /series. That list returns 16,643 series in one page, so a keyword scan is both incomplete and noisy: "gas" matched KXNBALASVEGAS (Las Vegas) and "golf" matched KXTRUMPGOLFD (a Politics market), while no category value covers gasoline at all.

Evidence: reports/verify-facts-raw.md §5 lists the false positives; reports/verify-facts-v3.md §G shows zero gas-price events in the open-event scan.

Status here: topics are matched on Kalshi's own category plus explicitly-scoped series/title patterns, and the gas page renders an explicit empty state with the reason instead of inventing rows. Residual fixed 2026-11-20 (session 2345e0dd): the root config still carried the same unsound /GAS/i pattern — it matched KXNBALASVEGAS and KXNATGASW — and the culture topic missed the literal Culture category that exists in the live demo vocabulary (4 series, data/probe/api_surface.json). The gas matcher is now the KXAAAGAS* family plus explicit exclusions (crude / WTI / Brent / natural-gas / diesel / Vegas / barrels / oil), and classifyEvent honours per-topic excludePatterns. 15/15 classification cases pass, including Natural gas price → none, Las Vegas → none, AAA gas price → gas.

F9 — Seconds-resolution price history does not exist mitigated

The limitation: the brief asked for a chart whose window can be seconds, minutes or hours. Kalshi's candle endpoint accepts only 1, 60 or 1440 minutes, and REST quotes are cached for a few seconds, so there is no seconds-resolution history to request.

Resolution: windows of 5 minutes and shorter are drawn from samples this page takes itself every 2 seconds, each stamped with the time it was read, and labelled "Accumulated live samples" so it is never mistaken for exchange history. Longer windows use real candlesticks.

Source: Candlestick intervals ↗ — confirmed by a live period_interval=5 request returning HTTP 400.

F10 — WebSocket streaming is documented but not wired in open

What is unverified: that the browser can open an authenticated WebSocket to the demo environment and receive ticker or orderbook_delta messages.

Why: the WebSocket handshake requires signed headers, and the connect signature covers timestamp + "GET" + "/trade-api/ws/v2". Sending custom headers from a browser WebSocket is not possible, so a browser-only stream would need a workaround this build did not validate.

Status here: polling is used instead, and each chart states which source produced its points. Streaming is listed on the questions page with what would be needed to confirm it.

Source: WebSocket quick start ↗

F13 — The shortlist chat is a tradeability screen, not a validated edge open

What is unverified: that the model screen identifies profitable trades. The screen sums points from six documented fields — open interest, spread, depth at the touch, price band, time to close and 24-hour volume — but no claim about expected return is made anywhere on the site.

Why: a price is not a probability unless someone says so, and the demo environment has no deep history to fit a probability model on. Claiming an edge would be a fabrication.

Status here: the Alerts page states the rule set and shows the score breakdown for every shortlisted swing. The Strategy Tester measures each signal's hit rate on settled demo markets and prints it next to the average price the signal paid, so the reader can judge the screen against data instead of against a claim.

Sources: Get Market ↗ Market settlement ↗

F14 — A price jump cannot be attributed to a cause from official sources open

What is unverified: that any particular news event caused any particular price swing. Kalshi's public API publishes no news feed and no causal link between an event and a price change.

What is available instead: GET /events/{event_ticker} returns settlement_sources — a list of official sources (name and URL) that Kalshi publishes for determining that event's outcome — together with the market's own rules_primary. Those links are shown under every alert and under the category charts.

Status here: they are labelled as where the market is decided, never as the cause of a move. Any stronger statement would be an inference the API does not support.

F15 — Simulated trades carry no fees, spread or slippage open

What is unverified: the true profitability of any strategy. A simulated fill is placed at the trade-close price of the candle that fired the signal, so it ignores the bid–ask spread, the size available at that price, and the fee schedule.

Impact: every simulated result on the Strategy Tester page is optimistic by an amount this site cannot quantify.

Status here: the assumption is printed in a warning panel above every backtest result, the fee schedule is linked from that panel, and no live strategy comparison is published.

F16 — The alert scan is bounded, so some swings are never reported open

What is unverified: that the alert feed has seen every open market on the demo exchange. Two bounds apply, both because the unauthenticated request budget is not published and must not be guessed at:

  • the Live alerts page keeps the top 30 markets per topic by money traded, and rescans the open-event list every 10 minutes;
  • the reusable engine behind the paper trader reads at most six pages of 200 open events — 1,200 events per poll.

Impact: a swing in a market outside the scanned window is not posted, and the "all events" chat is therefore "all qualifying swings within the scanned window", not "all qualifying swings on the exchange".

Status here: the bound and the number of events actually scanned are shown on the Live alerts page — under the feeds and in the scan summary line — so the coverage of the feed is always visible. The scan sizes are constants in assets/js/config.js and can be raised.

3 · Repository, coordination, and external-link irregularities

F17 — Prior NO-side simulator P&L used the YES quote as its entry cost mitigated

What was found: before this audit, NO-side backtests subtracted the YES contract quote from the NO settlement payout. For a binary contract, the NO contract entry price is the complement of the YES quote (1 − YES price), so prior NO-side P&L, capital and ROI were not reliable.

Correction: the Strategy Tester now computes NO entry cost as 1 − the returned YES quote and scores NO payout from 1 − settlement value. The simulator also has deterministic fixture tests for both outcomes. Results from earlier versions should not be relied upon; rerun a backtest to regenerate the corrected results.

Status: mitigated in the current simulator. No historical API data was edited or invented; the browser recalculates values from returned market and candle responses each run.

Sources: Market settlement ↗ Reciprocal YES/NO pricing ↗ Get market ↗ Market candlesticks ↗

A2 — Alerts are only recorded while the page is open open

What was found: polling runs in the browser tab. A move that happens while no tab is open is not recorded, and nothing is stored server-side. The poll interval is 5–60 seconds, so a move that starts and reverts between polls is not seen.

What was found: the alert compares last_price_dollars between two polls. Quote-only moves (bid or ask without a trade) do not alert, and a move that goes up and back down within one interval produces no alert.

Status here: the rule is stated on the page and unit-tested. Quote-mid alerts are not implemented.

1b · Defects found by this session (2026-11-20, re-review)

Found by reading every file again against the official API reference and against live demo responses fetched during this session. Each item names the source that proves it and says whether it was fixed in this session or is left open for review.

Y1 — Cancel sent no market_ticker, so non-shard-0 orders could never be cancelled fixed

What was found: cancelOrder(orderId) sent DELETE /portfolio/events/orders/{order_id} with no query parameters at all.

Why that is wrong: the Cancel Order (V2) reference documents market_ticker and exchange_index as query parameters and states that market_ticker is required for auto-routing; when exchange_index is omitted it otherwise defaults to shard 0. The sharding guide adds that an order can only be cancelled on the shard where it rests, and a request that reaches another shard is rejected with not_found / market_not_found, leaving the order untouched. Since every order write auto-routes by ticker, an order created on shard 1 or 2 (Crypto is shard 2 per the sharding table) could never be cancelled by the old call.

Fix shipped: cancelOrder(orderId, marketTicker) now requires the ticker and sends ?market_ticker=…; the Portfolio page asks for it before cancelling. The create call can additionally forward the market's own exchange_index, and omits it by default so Kalshi auto-routes.

Official sources: Cancel Order (V2) ↗ Exchange sharding ↗

Y2 — Liquidity read a field the API does not return fixed

What was found: the category pages summed yes_bid_size_fp + no_bid_size_fp for "resting size". no_bid_size_fp appears in neither the Get Market schema nor any live market object: markets carry only yes_bid_size_fp and yes_ask_size_fp. The second term was therefore always 0 and the figure read low.

Fix shipped: the sum now uses the two documented size fields and is labelled "resting size at touch, Σ yes_bid_size_fp + yes_ask_size_fp". A regression test fails if any module reads no_bid_size_fp again.

Official source: Get Market ↗ · live check: GET /events/KXAAAGASW-26NOV23 ↗

Y3 — Fees were displayed 100× too small fixed

What was found: the fills table rendered fee_cost_dollars ?? fee_cost / 100. Get Fills documents fee_cost as a dollar string ("0.5600" style, like yes_price_dollars); there is no fee_cost_dollars field in the schema, so the fallback always ran and divided real dollars by 100.

Fix shipped: the fee is read as the documented dollar value.

Official source: Get Fills ↗

Y4 — The board omitted multivariate (combo) events entirely fixed

What was found: every board scanned only GET /events. The Get Events reference says in as many words: "This endpoint excludes multivariate events. To retrieve multivariate events, use the GET /events/multivariate endpoint." Live demo combos exist and some bundle election legs, so "all events" was an incomplete statement for Elections and Culture.

Fix shipped: the combo endpoint is scanned for those topics and every combo is filed by resolving its documented mve_selected_legs — never by parsing its generic title ("yes Republican party,no Democratic party") — and is labelled as a combo with its legs shown. Combos whose legs cannot be read stay unclassified. Ten taxonomy tests cover this, including the mixed-topic case.

Official sources: Get Events ↗ Get Multivariate Events ↗ · live check: GET /events/multivariate ↗

Y5 — The strategy tester anchored settled-market history on "now" fixed

What was found: the tester asked for the last N minutes before the current clock, but a settled market's candles end at its settlement. For any market that settled more than N minutes ago the requested window contained no trading at all, so the replay saw no history and the strategy silently scored nothing.

Fix shipped: fetchCandles accepts an endTs anchor and the tester passes that market's own settlement_ts.

Official source: Get Market Candlesticks (required start_ts / end_ts) ↗

Y11 — "High-ROI model" remains a rule-based screen, and its inputs are unproven parameters open

What was found: the second scrolling chat is a select filtered by a transparent, documented-arithmetic screen (spread ≤ $0.05, open interest ≥ 1, price band 10–90¢). It is not a probability model and forecasts nothing. The new chance baseline on the Strategy Tester now makes that measurable: a strategy at or below the coin flip has shown no edge.

What would close it: a scored model with a held-out sample large enough to separate it from the control. That is research work, not a documentation check, and inventing a number here would be exactly the kind of fabrication this site refuses.

What is not flagged

For balance: these were checked and are correct —

  • The demo REST and WebSocket URLs in the brief match the official documentation.
  • Public market data really is readable without credentials, including order books and candles.
  • CORS genuinely permits this site's GitHub Pages origin — verified against nine endpoints.
  • Settled markets really do report result as yes or no; a 200-market sample contained 82 yes and 118 no, none blank.
  • Each market publishes its own price grid, so snapping order prices to it is correct rather than assuming a one-cent tick.
